## Attachment inspection: a material mismatch

The exact issue attachment was fetched and inspected without executing its contents:

https://github.com/user-attachments/files/30976419/Form.Validation-export-1786529294690.tar.gz

SHA-256: `ab29d1903dd42958a71b136e122d3edc2e54fd9fc48eaeecb927062c501df04d`.

Inspection job: https://github.com/AyobamiH/budibase/actions/runs/34066421984/job/101575861459

The exported form targets `table1`, whose primary display field is `required_display_column`. Both text fields have `presence: false`; the primary display requirement is separate from that flag.

The exported Save Row action has only `tableId` and `fields` parameters. It has no `providerId`, and its field override object has no entries. There is no visible public claim that this is the intended final configuration.

Consequently, the current candidate will not invoke a form callback for that exact action. Automatically guessing a form would risk changing supported non-form Save Row behaviour. This must be resolved through reproduction and scope agreement, not hidden by widening the patch.

Budibase documents an explicit Validate Form action before Save Row:

https://docs.budibase.com/docs/form-validation
