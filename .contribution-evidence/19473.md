## Confirmed failure mechanism

The real backend rejects an invalid save with this body:

```json
{"status":500,"validationErrors":{"required_display_column":["can't be blank"]}}
```

There is no `message` or general `error` property. The shared API client falls back to `Response.statusText`, but HTTP/2 has no status messages. The client notification handler previously required a truthy `message` before considering `validationErrors`.

A controlled real-browser comparison reproduced the consequence:

| Transport | Unchanged upstream | Final candidate |
| --- | --- | --- |
| HTTP/1.1 | Field error notification visible | Field error notification visible |
| HTTP/2 | Save rejected silently | Field error notification visible |

Chromium's network protocol observations confirmed actual `h2` responses with empty status text. The original exported action configuration reproduces this difference; it is not necessary to invent or mock an error response.

References:

- https://developer.mozilla.org/en-US/docs/Web/API/Response/statusText
- `packages/frontend-core/src/api/index.ts`, `makeErrorFromResponse`.
- `packages/client/src/api/api.ts`, `onError`.

The patch lets structured validation errors reach the existing notification handling independently of a general message, with a type-safe message-only fallback. Request/app suppression, ignored endpoints, recaptcha expiry, authentication banner priority and ordinary messages retain regression coverage. Save Row and form-validation semantics are unchanged.

This is a verified cause of the silent-error behaviour, not a claim to have inspected the reporter's authenticated cloud traffic.

## Scope and fixture caveat

Original attachment:

https://github.com/user-attachments/files/30976419/Form.Validation-export-1786529294690.tar.gz

SHA-256: `ab29d1903dd42958a71b136e122d3edc2e54fd9fc48eaeecb927062c501df04d`.

Its Save Row action has no `providerId` and no populated field overrides. Consequently it submits only the table ID, not the entered form values. The final patch reveals that failed save's error but deliberately does not guess a provider or rewrite the user's configuration. Controlled connected-provider cases verified corrected saves separately.

Automatic inline validation on every Save Row and precedence of custom client validation messages are separate behavioural questions, not changes made by this patch. Budibase's documented Validate Form action remains intact:

https://docs.budibase.com/docs/form-validation

The browser harness enables only the newly imported disposable app via the supported workspace-app endpoint. No authentication or role checks were bypassed. Earlier setup failures (admin bootstrap, workspace metadata ID vs app ID, published app route, and imported app disabled state) are superseded by the complete final run.
